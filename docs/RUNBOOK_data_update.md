# Runbook: adding a new NBK decision and new factor months

Follow the steps in order. Every number in the README, the docs and the dashboard is regenerated by the
commands below; never type a number by hand. `data/raw/` and `config/nbk_decision_dates.csv` are
append-only: add lines at the end, never change or delete an existing line
(`tests/test_data_contract.py` compares them with the last commit and fails otherwise).

## 0. Before the decision: log the forecast

1. `python run.py forecast-log` stores the current next-decision forecast in `docs/forecast_log.csv`
   (refused after the decision date or once the decision is in the data).
2. Commit and push `docs/forecast_log.csv` (and `data/processed/forecast_scores.json`,
   `outputs/forecast_scores.md`) immediately. The GitHub commit is the external timestamp.

## 1. Freeze the old version

1. Commit everything that is current (`git status` must be clean).
2. Tag it: `git tag before-data-update-YYYY-MM-DD` (date of the latest decision in the data) and
   `git push origin --tags`.
3. Set `COMPARE_TAG` in `src/compare.py` to the new tag (this is the only code change of an update) and
   record it in `docs/deviations.md` as part of the update's D-entry.

## 2. Find out what is needed

1. Add the new effective date as the last line of `config/nbk_decision_dates.csv` (source: the NBK
   schedule page, column «Дата установления базовой ставки»). Add its announcement date, press-release link
   and retrieval date as a row of `docs/nbk_announcement_dates.csv`.
2. `python run.py needs YYYY-MM-DD` (the new decision date, and the next upcoming one) prints, for each
   file, the reference month (decision month minus the assumed lag in `config/release_lag.json`), the base
   month of the 12-month growth, the month of the base rate, and whether each is already in `data/raw/`.
   Rows marked **MISSING** are what you must download.

## 3. Download and append

| File in `data/raw/` | Source (see `docs/facts_to_fill.csv`) | Column to append |
|---|---|---|
| `base_rate_history.csv` | NBK schedule page (rate after the decision; month = effective month) | `rate` |
| `inflation_history.csv` | stat.gov.kz element 1549 (CPI, year-on-year %) | `inflation` |
| `export_history.csv` | stat.gov.kz element 446905, national total row, «тыс.долларов США» | `exports_thousand_usd` |
| `import_history.csv` | stat.gov.kz element 446906, national total row, «тыс.долларов США» | `imports_thousand_usd` |
| `loans_legal_entities_history.csv` | nationalbank.kz file 135680, legal entities | `loans_legal_entities_mln_kzt` |
| `loans_individuals_history.csv` | nationalbank.kz file 135680, individuals | `loans_individuals_mln_kzt` |
| `consumption_history_updated.csv` | stat.gov.kz element 4084 (retail volume index, year-on-year %) | `consumption_yoy` |

1. Save every downloaded file unchanged in `data/incoming/` (not committed). Write down the page's update
   date and today's date as the retrieval date.
2. Append one line `YYYY-MM,value` per missing month, in the unit of the existing rows. Do not replace
   existing months even if the new edition revises them; list the revisions instead (step 6).
3. In `docs/facts_to_fill.csv`, update `publication_date` and `retrieval_date` of every file you downloaded
   again. If later rows come from a newer edition while the dates still describe the older one, say so in
   `notes` with the sentence "Publication date refers to the edition ending YYYY-MM." and state the newer
   edition's dates (or UNKNOWN). Keep the note "Upper bound from file update date: N days" equal to the value
   `python run.py facts` prints in `outputs/release_lag_check.md` (the tests compare them).

## 4. Rebuild, in this order

```
python run.py data      # panel + raw-data jump screen (outputs/data_anomalies.md)
python run.py model     # re-estimates the frozen specification on the new split
python run.py robust    # exploratory stress tests
python run.py report    # OLD vs NEW comparison, numbers_for_note.json, README
python run.py facts     # provenance, limitation texts, generated docs, README
python run.py check     # rebuilds everything in a temporary folder and compares
python -m pytest -q -k "not check_01"
python run.py forecast-score   # scores logged forecasts whose decision is now in the data
```

`python run.py all` runs data → facts and the tests in one go; `check` and `forecast-score` are separate.

## 5. Compare before and after

1. `python run.py compare` prints `outputs/version_comparison.md`: usable decisions, the estimation and
   holdout windows, headline score and band, next-decision probabilities, the RMSE ratio with its bootstrap
   interval and Diebold–Mariano p, RPS, the joint LR test, Holm-significant slopes, the stability test and
   the robustness count, OLD vs NEW.
2. Check `outputs/data_anomalies.md`: a new flag that enters the latest score must be checked against the
   publisher before the result is used. Never change a flagged value; record the check in `TODO_HUMAN.md`.
3. `python run.py data` prints the rebuild comparison: "Differing cells: 0" for the decisions that were
   already in the panel. Any other number means an existing row changed; stop and find out why.

## 6. Record

1. `docs/manual_steps_found.md`: a row per appended line (date, file, row, source URL, sheet/row/column,
   manual step), and any revisions between editions.
2. `docs/deviations.md`: the next free D-number (what changed / why / what the original produced) for
   anything that is not a plain append: a changed tag, a changed rule, a new check.
3. `TODO_HUMAN.md`: every fact you could not confirm, as UNKNOWN.
4. Commit and push. The CI workflow (`.github/workflows/tests.yml`) runs the tests and the check on Linux
   and Windows.

## What must not change

The main specification, its chronological split (last ceil(20%) of usable decisions as holdout), the
RMSE-ratio verdict rule and the estimator are frozen (`docs/development_plan.md`). An update re-runs them; it
never tunes them. Candidate improvements follow the promotion rule in `docs/development_plan.md`.
